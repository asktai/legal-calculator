## 2026-10-20 ｜ 保全费拆两个计算器 ＋ 发现「包内脚本根本跑不起来」

> **开发者指令原文**：「财产保全费用（含保险费）这个不对，应是两个计算器，一个是财产保全费计算器，
> 一个是财产保全担保费计算器。有些场景只需要计算保全费用。」

### 一、按指令拆分（44 → 45 个计算器）

`preservation-fee` 原把法院收的**保全申请费**与保险公司的**保全保险费**加成一个
"保全总支出"，属**性质混算**：前者是诉讼费（可计入诉讼请求、由败诉方负担），
后者是商业投保支出（法院不代收代付）。已拆为：

- **财产保全费**（`preservation-fee`）：第 14 条第（三）项，30 元起、1%／0.5% 累进、**5,000 封顶**；
- **财产保全担保费**（`preservation-guarantee-fee`）：保险 / 银行保函 / 现金担保三分支，
  现金分支只算资金占用成本、明确"外部费用 0 元"；引《财产保全案件若干问题的规定》第 5 条（担保上限 30%）。

两页互给交叉指引，避免"只算法院那笔"或"漏了担保那笔"。审计用例 68 → 70
（封顶 / 未封顶 / 保险 / 现金各一条）。

### 二、验收时发现一个**一直存在、被软链掩盖**的真缺陷

出包后按 `DEV_SPEC` 的"解包到临时目录"验收，四个脚本全部报
`Cannot find module '../../src/core/calculators'`。

**根因**：`skill/scripts/*.ts` 都用 `import '../../src/core/...'`，而技能包**只发 `skill/`、不含 `src/`**。

**为什么历次发版都没发现**：本机安装目录是软链
`~/.codebuddy/skills/legal-calculator -> /workspace/legal-calculator/skill`，
`../../src` 顺着软链正好退回开发仓库，**条件成立**。只要真实解包（任意目录）就必崩。

**这正是甲组缺口 7「实例测试无独立关卡」的实际代价**——不是理论风险，是已经在每一版包里发生的事实。
缺口 7 的暂代手段写的是"发版前手工解包到临时目录跑一次 `smoke.ts`"，此前**从未真正执行过**；
一旦执行，第一秒就会炸。

**修法**（不是打补丁，是补通道）：

| 件 | 作用 |
| --- | --- |
| `scripts/build-skill-bundles.mjs`（新增） | 把 `src/core` 的计算器注册表／报告导出内联成 `skill/lib/*.mjs`；`version.mjs` 由 `SKILL.md` 生成，保证包内版本与包一致 |
| `scripts/core-loader.ts`（新增） | 统一装载顺序：**先包内 `lib`，再开发侧 `src`**；只吞"模块不存在"，真实运行错误照抛 |
| `check.ts` 安装形态分支 | 包内自检：结构、版本三处一致（SKILL＝CARD＝lib/version）、45 个计算器可载入并试算 |
| `xlsx` 改 `createRequire` | 唯一无法内联的依赖，缺时给「`npm i xlsx`」明确指引，不静默失败 |

**路径与转译两个坑**（都是实测撞出来的，不是推理出来的）：

1. 第一版装载器用 `await import()`。开发侧正常，**装包后**报
   `Top-level await is currently not supported with the "cjs" output format`——
   `tsx` 把 `.ts` 转成 CJS 执行，顶层 await 直接不合法。改 `createRequire` 同步加载。
2. `check.ts` 的 `ROOT = scripts/../..` 在软链下指向开发仓库、在真实安装下指向**包外**，
   包内自检因此报"全都缺"。加 `PKG = scripts/..`，安装形态以 `BASE = PKG` 解析。

## 2026-10-20 ｜ 修复：项目档案填写互相清空（使用者报告）

> **开发者指令原文**：「律师服务费项中，填写项目名称，再选择时间，前面填写的就清空了，
> 填写第项目人也是，添加当事人也是」＋ 截图。

### 一、根因

`ProjectMeta` 组件发出的是**增量 patch**（如改时间只发 `{date}`），而 `CalcPage.tsx:93`
把 `onChange` 直接接到了 `setMeta`——React 的 setState 传对象是**整体替换**，
于是每填一项就把其余字段全部抹掉。三条报告路径（填名称→改时间、填项目人、加当事人）同根同源。

**对照**：报告中心（`ReportBuilder.tsx`）的 `updateItem` 是 `{ ...it, ...patch }` 合并写法，
故同一组件在报告中心**无此病**——恰好证明问题在调用方，不在组件。

### 二、修法

`CalcPage.tsx` 改为 `onChange={(patch) => setMeta((prev) => ({ ...prev, ...patch }))}`，
并加注释说明为什么必须合并（防止将来又被"顺手"改回）。

### 三、验证（端到端，真浏览器）

写 `maint/scratch/verify-meta-fix.cjs`（puppeteer-core 驱动本机 Chromium），
在「律师服务费」页按报告路径实走 11 步断言：**修复后 11/11 全过**；
**把修复临时还原，7 项当场失败**（正是报告的三条路径）——判据有区分度，不是恒真。
复跑：tsc 0 错、audit 68/68、check.ts FAIL 0。三件套已重出。

**教训**：同一组件在两处使用、一处合并一处替换——**契约（patch 语义）没有写进类型**，
`onChange: (patch) => void` 与 `(prev) => void` 形状相同但语义相反，类型系统拦不住。
后续如再遇"传函数即清空"，先查调用方是合并还是替换。

**瘦身（2026-10-30）｜ `examples/示例报告.png` 4.2 MB → `report-longshot/` 三段 WebP 2.2 MB**

用户问「skill 包与 zip 包容量为什么差那么多」，分析后确认属设计使然（`.skill` 只含 `skill/`，

占 `.zip` 的四分之一。用户拍板瘦身，方案取「切分 + 换编码」组合：

- **为什么不整张转 WebP**：WebP 硬上限 16383 像素，25124 高直接报
  `Image size exceeds WebP limit`。缩放到 16000 高以内会牺牲可读性（宽度从 1800 缩到 1146），
  弃用。**等高三段切分**（各 ~8375px）+ q88 WebP，保持原分辨率 1800 宽。
- **q88 可读性抽检**：法条小字、表格数字、封顶减负等关键内容逐字清晰，与 PNG 无肉眼差。
- 产物：`examples/report-longshot/示例报告-长图-{1,2,3}.webp`（709 / 779 / 815 KB），
  原 `示例报告.png` 删除（`examples/` 总量 4.4 MB → 2.5 MB，`.zip` 相应减重 ~1.7 MB 解压后）。
- 与其余 `示例报告.*` 同一份数据（同一 report.sample.json 导出），切分边界落在条目间空白带。

启示：**长图示例别存单张 PNG**——超长内容（>16383px）WebP 装不下、PNG 压不动，
两头的亏都吃。要么切分段（保原分辨率），要么缩放（牺牲清晰度），发布物里前者更合适。
